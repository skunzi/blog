The Static That Died Twice

SEP 02, 2026 9 min read

A field report from debugging a "double free or corruption (!prev)" crash that only showed up after all tests had already passed.

The log that shouldn't exist

[==========] 24 tests from 1 test suite ran. (158 ms total)
[  PASSED  ] 24 tests.
double free or corruption (!prev)

Read that again. Every assertion passed. GoogleTest printed its green PASSED banner. And then, with no test left running, the process reached for a chunk of heap memory that had already been freed, and aborted with exit code 134 (SIGABRT). That was enough to make the Bazel test suite fail even though all tests had already passed.

There was no flaky assertion to blame, no obviously broken mock, not even a stack trace pointing at test code. Whatever was wrong lived after the tests were over, in the machinery almost nobody ever looks at: global static teardown.

This is the story of tracking that crash down to its actual cause: a single class-static object that, thanks to how the build was wired up, existed twice in the same process and got destroyed twice at exit.

TL;DR for the impatient

The same small "settings" library got linked into one test binary through two different routes: once built from source into a shared library, once as a prebuilt static archive baked directly into the executable. A mutable, exported class-static object inside that library therefore existed as two physical copies, yet the dynamic linker's symbol resolution silently collapsed both copies onto a single address. Both copies' constructors ran against that one address, and at shutdown both copies' destructors ran against it too, freeing the same allocator buffer twice. Nobody wrote a bug to cause this. It was an emergent property of the build graph.

Act 1: "It says PASSED, so why did CI go red?"

The first reaction to a failure like this is disbelief. Exit code 134 means SIGABRT, but every assertion in the test suite succeeded before it. The crash happens strictly after RUN_ALL_TESTS() has returned.

The instinctive first suspects were the usual ones: a use-after-free in test fixtures, a bad mock lifetime, maybe a threading issue at shutdown. All of those were ruled out quickly, because the crash reproduced identically as a single, deterministic, single-threaded test with nothing exotic in it. That's a strong signal you're not looking at "normal" memory corruption. You're looking at something structural.

Act 2: symbol table archaeology

The binary in question is built from a large, modular C++ codebase, using a Bazel-like build system. Buried in its dependency graph is a small "settings" library (call it SettingsEngine) used by dozens of other components to read configuration from JSON. SettingsEngine ships a helper class, DocumentReader, that keeps a "canonical empty document" around as a fallback value, backed by a small pooled allocator:

class DocumentReader {
public:
    static const Document& getEmptyDocument();

private:
    static Document s_emptyDoc;   // owns a pooled allocator internally
};

Nothing unusual there. This pattern exists in thousands of codebases. The next step was to stop guessing about test code and start reading the binary itself. nm on the test executable and on every shared library it loads, grepping for that static:

$ nm -CD ./test_binary            | grep s_emptyDoc
0000000000123456 B DocumentReader::s_emptyDoc

$ nm -CD libsettingsengine.so     | grep s_emptyDoc
0000000000034560 B DocumentReader::s_emptyDoc

Two hits. Both B (bss, meaning uninitialized/zero-initialized static storage), in two different binary images. That single observation reframed the whole investigation: this isn't a lifetime bug in test code, it's a duplicated global across a shared library and the executable that statically links the same source.

A quick pass with ldd and strings over the executable confirmed the suspicion further: the same header/source pair for DocumentReader had been compiled from two different physical locations on disk (once from the monorepo checkout, once from an unpacked vendored binary package) and both copies had made it into the final link.

Pulling on that thread led straight to the dependency graph, and the actual source of the duplication: two unrelated build modules each declared their own dependency on "the settings engine" (one on the source repository, one on a prebuilt binary release of the same library) and nothing in the build graph deduplicated them.

DocumentReader.cpp was being compiled twice, into two separate binary artifacts that both ended up loaded into the same process. That explains the two nm hits, but not yet why destroying one of them would corrupt the other. For that, the backtrace of the crash itself was next.

Act 3: the backtrace names the crime scene

With a debug build in hand, the crash itself pointed straight at the destructor:

#7  _int_free ()
#8  __GI___libc_free ()
#9  DocumentReader::~DocumentReader ()
      -> code inside the TEST EXECUTABLE itself
#10 __cxa_finalize (d=0x7ffff7dbd000)
#11 libsettingsengine.so
      -> destructor registration OWNED BY THE SHARED LIBRARY
#13 _dl_fini ()

That is a strange stack: the destructor body executing is the copy compiled into the executable, but it's being invoked from the exit machinery that belongs to the shared library. Two different modules, one function body, one call chain. That mismatch was the thread worth pulling.

Act 4: the conditional breakpoint that made it undeniable

At this point the working theory was: "there might be two objects being destroyed, and one of the destructions is invalid." To prove it, the fix was to stop looking at code and start looking at addresses, with a conditional breakpoint on the destructor, gated on the specific instance:

break DocumentReader::~DocumentReader if $rdi == &DocumentReader::s_emptyDoc
run

The result settled the question completely:

HIT #1  -- called from __run_exit_handlers   (executable's atexit chain)
HIT #2  -- called from __cxa_finalize of the .so (shared library's teardown)

double free or corruption (!prev)
Program received signal SIGABRT, Aborted.

TOTAL DESTRUCTOR CALLS ON THIS ADDRESS = 2

Both hits fired on the exact same address. Not two different objects at two different addresses, but the same object, destroyed twice, by two independent teardown mechanisms that both believed they owned it.

The mechanism: how two objects become one

This is the part that makes the bug genuinely interesting rather than "just a duplicate symbol." If the executable and the shared library really had two independent, isolated copies of s_emptyDoc, each would construct its own instance and destroy its own instance without any crash. The reason they instead collide on one address comes down to how position-independent shared libraries resolve global symbols.

Because the class-static has ordinary (exported) visibility and the shared library is compiled position-independent, every access to s_emptyDoc, even from the translation unit that defines it, goes through a level of indirection (the GOT), rather than a hard-coded address. This is required by the shared-library ABI: if some other module in the process were to override the symbol, all consumers, including the "owning" module, must observe the same, single, global definition. It's the exact mechanism that lets you override malloc process-wide with LD_PRELOAD.

When the same symbol name is exported by both the executable and a shared library, the loader's global symbol resolution has to pick one winner for the whole process, and the executable's own definition consistently wins over anything a shared library brings in. So both GOT entries end up pointing at address A, the executable's copy. Address B still physically exists (that's the second nm hit), but it's orphaned; nothing ever dereferences it through the normal symbol-based path.

Two independent modules each believe they own a private static object. Both constructed "their" instance. Both registered a teardown callback for "their" instance. But symbol resolution silently made both callbacks target the same memory, so the allocator's internal chunk pointer gets freed once by the executable's teardown and then freed again by the library's teardown. Classic double free, just arrived at through linkage rather than through application logic.

Why this is sneaky

  • Every individual test passes. The corruption only manifests during global teardown, which almost nobody single-steps through.
  • nm and ldd look "normal" at a glance. Duplicate symbols across a static archive and a shared object are common and usually harmless (each module just uses its own copy). It's only exported, mutable, class-static data that turns this into a landmine.
  • The bug isn't in any one team's code. DocumentReader is fine in isolation. The test helper library is fine in isolation. The production populator libraries are fine in isolation. The defect is an emergent property of a build graph in which two independent dependency edges resolve to different builds (source vs. prebuilt binary) of the same library.
  • The crash signature (double free or corruption (!prev)) points you toward "someone freed a pointer twice," which is true, but the actual bug is one level up: "someone constructed the same static object twice, from two different modules, without either module knowing about the other."

Fixing it

Two complementary fixes emerged:

  1. Collapse the build graph. Make sure only one dependency edge (source or prebuilt, never both) ever reaches a given library inside one binary. This is the real fix: it removes the duplicate compilation entirely, so there is only ever one definition to link and one object to construct/destroy.

  2. Harden the library against accidental double-linkage. Replace the class-static object with a function-local static inside an accessor function:

    const Document& DocumentReader::getEmptyDocument() {
    static Document emptyDoc{};   // constructed on first call, once
    return emptyDoc;
}

    A function-local static's initialization guard variable is itself subject to the same GOT-based symbol resolution, so even if the function body ends up duplicated across a shared library and an executable, only one guard variable is ever live at the shared address, so construction (and the __cxa_atexit registration that comes with it) happens exactly once, no matter how many times the containing library is accidentally linked into the same process. This doesn't fix the underlying build-graph duplication, but it makes the library itself immune to this entire class of crash.

Takeaways

  • If a process aborts with a memory-corruption signature strictly after tests report success, look at global/static teardown, not your test code.
  • nm/ldd across every loaded module is cheap and can immediately turn "a vague heap corruption" into "a duplicated symbol."
  • A conditional GDB breakpoint keyed on a specific address is the single most decisive tool for telling apart "two different objects" from "one object, destroyed twice."
  • Mutable, exported class-static objects are quietly dangerous in any codebase where the same library can plausibly be linked in more than one form (source vs. prebuilt, static vs. shared) into the same binary. Prefer function-local statics, or avoid mutable global state entirely.
  • Fixing the symptom in the library (function-local static) and fixing the root cause in the build graph (deduplicate the dependency) are both worth doing: one makes the crash impossible, the other makes the duplication itself go away.

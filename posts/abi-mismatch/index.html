The Segfault That Passed Code Review

AUG 09, 2026 9 min read

How a Conan profile still set to libstdc++ in a libstdc++11 monorepo turned every std::filesystem::path crossing a library boundary into a silent memory-layout disagreement, and why the segfault took weeks to find.

The crash

$ bazel test //services/ingest:config_parser_test
...
Signal: SIGSEGV (Segmentation fault)

No assertion failed. No sanitizer fired during the build. Just a clean segfault, not in a complex computation or a file operation, but in a destructor:

void ConfigParser::loadFrom() {
    std::unique_ptr<std::filesystem::path> config_path(
        static_cast<std::filesystem::path*>(
            configlib_create_path("/usr/share/config/app.conf")  // extern "C"
        )
    );

    std::ifstream file(config_path->c_str());
    // ... parse configuration ...
}   // <-- SIGSEGV here, when unique_ptr runs the destructor

The path string was valid. The file was opened and read successfully. The crash came at scope exit, when the unique_ptr ran the destructor on a perfectly ordinary-looking path object. Nothing about the code itself explained a crash, and nothing in the code review two weeks earlier had raised a flag. That's because the bug wasn't in the code. It was in how the code was built.

A field that wasn't there

The backtrace was short and pointed deep inside the standard library:

#0  std::filesystem::__cxx11::path::_List::_Impl_deleter::operator()() ()
       from /lib/x86_64-linux-gnu/libstdc++.so.6
#1  std::filesystem::__cxx11::path::_List::~_List() ()
#2  std::filesystem::__cxx11::path::~path() ()
#3  ConfigParser::loadFrom() ()
       at config_parser.cpp:47

The crash was inside ~path(). C++ destroys members in reverse declaration order, so the destructor started with the last member: _M_cmpts, the parsed-component storage. In the new ABI, _M_cmpts sits at offset +32 inside the path object. But the library had built a 16-byte old-ABI path. Offset +32 was 16 bytes past the end of the actual object. The destructor read whatever happened to be in adjacent memory, interpreted it as a unique_ptr<_Impl> (a pointer to the component storage implementation), and tried to dereference it. The value there was 0x1a — unmapped memory. SIGSEGV.

In GDB, a raw dump of the memory at the path pointer showed what was happening:

(gdb) x/5gx config_path
0x55a3e890:  0x000055a3e8c8  0x000055a3e8f0
0x55a3e8a0:  0x0000000000000000  0x0000000000000041
0x55a3e8b0:  0x000000000000001a

The first two quadwords (16 bytes) were the actual path object: a COW data pointer and the old-ABI _M_cmpts. Everything after was outside the object — heap metadata and the start of the string's COW control block. The value at offset +32, 0x1a (26 decimal), was the COW block's _M_length field — literally the string length of "/usr/share/config/app.conf". The new-ABI destructor read that string length as a pointer and tried to follow it.

The question shifted from "what's wrong with the code" to "what's wrong with the object."

The sizeof that explained everything

The next diagnostic was crude but decisive:

// Added to the test (compiled with GCC 12, libstdc++11):
std::cerr << "sizeof(path) in test: " << sizeof(std::filesystem::path) << "\n";

// Added to the library that constructs the path (compiled with GCC 8, libstdc++):
std::cerr << "sizeof(path) in lib:  " << sizeof(std::filesystem::path) << "\n";
sizeof(path) in test: 40
sizeof(path) in lib:  16

Forty bytes versus sixteen. The library allocated a 16-byte old-ABI path. When the consumer's unique_ptr went out of scope, it ran the new-ABI destructor, which expected a 40-byte object. The destructor tried to clean up _M_cmpts at offset +32 — 16 bytes past the end of the real object — read garbage from adjacent memory, interpreted it as a pointer, and crashed dereferencing it. That's the crash.

The reason for the size difference is std::string. std::filesystem::path stores its pathname as a std::string internally. And std::string has two different memory layouts in libstdc++, controlled by the _GLIBCXX_USE_CXX11_ABI macro (or, in Conan terms, the compiler.libcxx setting).

The old layout (libstdc++, _GLIBCXX_USE_CXX11_ABI=0) uses copy-on-write (COW) with a single pointer to a heap-allocated control block. The new layout (libstdc++11, _GLIBCXX_USE_CXX11_ABI=1) uses the small string optimization (SSO) with inline storage for short strings:

These are different sizes: 8 bytes versus 32 bytes on x86-64. You cannot hand one to code expecting the other. And since std::filesystem::path contains a std::string, the path inherits the mismatch:

libstdc++ (old) libstdc++11 (new)
_M_pathname (std::string) 8 bytes 32 bytes
_M_cmpts (component storage) 8 bytes 8 bytes
Total sizeof(path) 16 bytes 40 bytes

That explained both the GDB output and the crash. The first 8 bytes of the old-ABI object were a heap pointer, which the new-ABI consumer also interpreted as a heap pointer (both ABIs store a pointer at offset 0). So GDB could read the actual string content. But bytes 8–15 of the old object, the component storage, were interpreted as the string length, producing a nonsensical value in the trillions. And bytes 16–39, which the consumer expected to find, didn't belong to the path object at all. The destructor only needed to read _M_cmpts at offset +32 to crash — the garbage there was a string length (26), which it dereferenced as a pointer to unmapped memory.

Why the linker didn't save us

libstdc++ has a safety mechanism for catching this kind of mismatch. New-ABI types like std::string live in an inline namespace __cxx11, so old-ABI and new-ABI strings mangle differently:

Old ABI:  std::basic_string<char>
New ABI:  std::__cxx11::basic_string<char>

If you try to link a function that takes std::string across the ABI boundary, the linker rejects it with an undefined symbol error. Since GCC 11, std::filesystem::path also lives in the __cxx11 namespace:

Old ABI:  std::filesystem::path
New ABI:  std::filesystem::__cxx11::path

A direct C++ function taking const path& mangles differently between ABIs, and the linker would reject it.

But our Conan library's public API used C-linkage wrappers, a common pattern for packages intended to work across compiler versions. Path objects were returned through extern "C" functions as opaque pointers and cast back to std::filesystem::path* on the consumer side. C linkage strips all C++ type information from the symbol, so the linker saw matching, undecorated symbols on both sides and was satisfied. It had no way to know that the pointer referred to a 16-byte object the consumer would read as 40 bytes.

Link-time success only proves symbol compatibility. It does not prove ABI compatibility. In our case, the binary linked cleanly, ran successfully, and crashed in a destructor.

A profile nobody remembered

With the mechanism understood, the question was: how did an old-ABI library end up in a new-ABI build?

The answer was in Conan. Our monorepo used Conan to manage a handful of external C++ dependencies. One of them, a configuration-file parser, depended on a utility library that exposed std::filesystem::path in its API. The Conan profile used to build and cache these packages:

# conan_profile_legacy
[settings]
os=Linux
compiler=gcc
compiler.version=8
compiler.libcxx=libstdc++
build_type=Release

That compiler.libcxx=libstdc++ is the problem. It tells Conan to build with _GLIBCXX_USE_CXX11_ABI=0: the old, COW-based string layout. The monorepo's own Bazel toolchain used GCC 12 with the default libstdc++11 (new ABI). No one had updated the Conan profile when the monorepo migrated compilers, because no one remembered it existed. The Conan packages were cached in the CI artifact store, built months ago, and just kept working until someone added a code path that passed a std::filesystem::path across the boundary.

The misconfiguration had been latent the entire time. Simpler types like integers, plain structs, and C strings had crossed the C-linkage boundary without issue because their layouts don't change between ABIs. It was only when someone added a code path that passed a std::filesystem::path through the opaque-pointer interface that the layout mismatch became a runtime fault.

What we changed

The immediate fix was one line: update the Conan profile.

# conan_profile (updated)
[settings]
os=Linux
compiler=gcc
compiler.version=12
compiler.libcxx=libstdc++11
build_type=Release

Rebuild and re-cache every Conan package. Segfault gone.

But "update the profile" is a fix for this incident, not for the class of problem. Three things changed to make it harder for this to happen again:

A compile-time ABI canary. A header shared between the Conan packages and the monorepo now checks both the compiler version and the ABI:

#if defined(__GNUC__) && __GNUC__ < 12
#error "This library must be built with GCC 12+ to match the monorepo toolchain."
#endif

#if _GLIBCXX_USE_CXX11_ABI != 1
#error "This library must be built with the C++11 ABI (compiler.libcxx=libstdc++11)."
#endif

This turns a silent runtime segfault into a loud compile-time error.

Profile generation from the toolchain. The Conan profile is now generated from the same toolchain definition that Bazel uses, rather than being a hand-maintained file that can drift.

C types at package boundaries. Where a Conan-provided library needs to exchange paths with the monorepo, the interface now uses const char* rather than std::filesystem::path. The conversion to path happens on the caller's side, in code compiled with the caller's toolchain. This removes path from the ABI surface entirely.

What makes this class of bug hard

Every defense you'd normally rely on is absent:

  • No compiler warning. Both sides compile cleanly. The mismatch is between translation units that never see each other's source.
  • No linker error. The __cxx11 inline namespace catches ABI mismatches for types like std::string and std::filesystem::path in direct C++ function signatures. It cannot help when objects cross the boundary through C linkage, dlopen, or type erasure.
  • No sanitizer catch (by default). ASan and UBSan instrument a single build. They don't detect layout disagreements between separately compiled artifacts unless you rebuild everything under a single, consistent toolchain, which is exactly the thing that wasn't happening.
  • The crash is non-local. The segfault occurs in the consumer, not in the producer. The library that built the wrong-layout object runs fine; it's the code that reads the object under the wrong assumptions that dies.

And even beyond the libstdc++ / libstdc++11 flag: std::filesystem::path is not ABI-stable across libstdc++ versions at all. Its internal representation (the component storage, the parsing logic, the helper types) changed between GCC 8 and GCC 9 when the implementation moved from the separate libstdc++fs static library into the main libstdc++.so, and continued to evolve through GCC 11 and 12. Types like std::string and std::vector were explicitly frozen after the ABI transition, but std::filesystem::path, std::regex, and other newer types were not part of that freeze.

If your build system consumes prebuilt C++ binaries through Conan, vcpkg, system packages, or anything else, both the libcxx setting and the compiler version are load-bearing. Every unfrozen standard library type you expose across that boundary is a bet that both sides were built with the same libstdc++. When the bet is wrong, nothing tells you until a destructor reads a string length as a pointer and segfaults.

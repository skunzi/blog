What the GitHub Contribution Graph Actually Measures

OCT 25, 2026 4 min read

tl;dr: The contribution graph reflects which commits reach the default branch and when, not how much work a developer does, and a clean Git workflow can make it look sparse.

Background

I keep my Git history tidy. Instead of stacking “address review comments” commits on a branch, I usually amend the existing work and force-push:

git reset --soft origin/main     # or the branch's merge base
git add -A
git commit -m "Add retry handling to the sensor adapter"
git push --force-with-lease

Before opening a pull request I squash the branch into one or two commits. The result is a history that is easy to review, bisect and revert.

While comparing contribution graphs at work, I noticed mine looked very different from my colleagues’: pale, with long empty stretches. Checking those stretches against my actual activity showed the work was there. The graph simply wasn’t recording it.

What counts as a contribution

According to GitHub’s documentation, a commit appears in the graph only if all of the following hold:

  • It is authored with an email address that is linked to your GitHub account.
  • It is reachable from the repository’s default branch (or the gh-pages branch).
  • It sits in a repository you have access to, and, for private repositories, you have enabled showing private contributions on your profile.

Opened pull requests, issues and reviews also count as contributions. Commits that only exist on a feature branch do not, until they are merged.

Please verify the details against the current GitHub docs, as the rules have been adjusted over the years.

How common Git workflows affect the graph

Practice Effect on the graph
Many small commits, merged with a merge commit Every commit is kept, so activity shows up on the days the commits were authored
Rebase and merge Commits keep their author dates and appear individually
Squash and merge One commit lands on the default branch, typically dated at merge time
Local squash or reset --soft before pushing Intermediate commits never reach a remote branch, so they are never counted
Force-push over an existing branch Replaced commits become unreachable and are never counted
Long-lived feature branch Nothing is counted until the merge, then everything lands at once

The graph therefore records integration events, not effort. Squashing five days of work into one commit produces one contribution on one day.

Why a dense graph is ambiguous

A dark graph is consistent with high output, but it is equally consistent with other causes:

  • Commits that are never squashed, such as WIP commits, typo fixes and formatting changes.
  • A team convention of merging with merge commits, which preserves every intermediate commit.
  • Direct pushes to the default branch.
  • Automated or mechanical commits, for example from bots or generated code.

Similarly, a sparse graph can hide a lot of work: debugging, design discussions, investigation, reviews outside GitHub, or a fix that took two weeks to find and consists of three changed lines. Work in tools other than GitHub does not appear at all.

The metric problem

The graph was designed as a personal activity overview, not as a performance measure. Using it as one runs into Goodhart’s law: once a measure becomes a target, it stops being a good measure. If people treat dense graphs as a sign of productivity, the incentive is to commit often, avoid squashing and avoid rewriting history, which is the opposite of what many teams consider good practice.

It is also worth being honest about the effect this has on perception. I found myself being impressed by colleagues’ graphs before I understood how they are computed, and I doubted my own performance when mine looked different. A signal with this much noise should not influence how we judge each other.

So what does the heatmap actually tell you? At best, a diffuse mix of activity frequency and commit hygiene. A dense graph means someone integrates many commits to the default branch; a sparse one means they don't. Neither says anything reliable about the volume or quality of work behind those integrations.

Recommendations

  1. Keep your history clean if you value it. A green graph is not a good reason to change your workflow.
  2. Do not use the graph to evaluate colleagues or yourself. Outcomes are better indicators: problems solved, review quality, reliability of shipped changes and knowledge shared with the team.
  3. If you have to compare activity, use data that matches the question, such as merged pull requests, review turnaround or lead time, and interpret them with context.

Conclusion

The contribution graph shows which commits were merged to the default branch and on which day. It does not show how much work was done. Developers who squash and rewrite history will look less active than those who do not, so the graph is a poor basis for any comparison between people.

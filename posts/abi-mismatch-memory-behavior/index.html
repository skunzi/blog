ABI Mismatch Under the Hood

AUG 16, 2026 11 min read

This is a companion to The Segfault That Passed Code Review. That article covers the debugging story and the Conan profile that caused it. This one goes deeper into the mechanics: what the compiler bakes into your binary, how the memory layouts differ byte by byte, and exactly what goes wrong when the two meet at runtime.

How std::filesystem is linked

std::filesystem didn't always live where it does today. Its home in libstdc++ shifted between GCC 8 and GCC 9, and that shift matters for understanding what the runtime expects.

GCC 8: The filesystem implementation shipped in a separate static library. You had to link it explicitly:

g++ -std=c++17 main.cpp -lstdc++fs

libstdc++fs.a was a static archive. When you linked against it, the compiled filesystem routines (including parent_path(), filename(), and the parser) were copied directly into your binary. Your executable carried its own private copy of the implementation, baked in at link time.

GCC 9 and later: The implementation moved into the main shared library, libstdc++.so. No extra flag needed:

g++ -std=c++17 main.cpp    # links libstdc++.so automatically

The filesystem routines now live alongside std::string, std::vector, and everything else in the same shared library your binary loads at startup.

This transition matters. With GCC 8, the implementation of parent_path() lives in your binary, compiled when you compiled, with whatever ABI flags you used. With GCC 9+, parent_path() lives in the shared library on the system, compiled once with the ABI that the system's libstdc++ was built with. If your binary creates a path object with one ABI and then hands it to a libstdc++.so that was built with a different ABI, the two sides disagree on the object's memory layout. That disagreement is the root cause of the crash.

What happens when you create a path object

When you write this:

std::filesystem::path p("/usr/share/config/app.conf");

several things are decided at compile time, before the program ever runs.

The header defines the layout

The compiler reads the <filesystem> header, which includes bits/fs_path.h. That header contains the class definition for std::filesystem::path. Stripped to the essentials:

// Simplified from bits/fs_path.h
class path {
    // ...
private:
    std::string  _M_pathname;   // the full path as a string
    _List        _M_cmpts;      // parsed path components
};

From this definition the compiler determines the exact byte-level layout of the type: total size, offset of every field, alignment requirements. Not an approximation, but the precise numbers that will appear as constants in the generated machine code.

Since path contains a std::string as its first member, the layout of path depends on the layout of std::string. And std::string has two layouts in libstdc++, controlled by the _GLIBCXX_USE_CXX11_ABI macro:

  • Old ABI (_GLIBCXX_USE_CXX11_ABI=0): std::string is 8 bytes: a single pointer to a heap-allocated control block that stores the length, capacity, reference count, and character data together (copy-on-write).
  • New ABI (_GLIBCXX_USE_CXX11_ABI=1): std::string is 32 bytes: a pointer, a length, and a union holding either a 16-byte inline character buffer or a capacity value (small-string optimization).

Which layout the compiler uses depends entirely on which ABI flag was active when the header was parsed. The same header, the same field names, two completely different memory layouts.

The layout is baked into your binary

This is the critical point. The compiler does not generate code that asks "how big is std::filesystem::path?" at runtime. It already knows. The size is a compile-time constant, fixed the moment the header was parsed.

Every operation the compiler generates (stack frame allocation, field access, copying, passing by reference) uses hardcoded offsets derived from the header. If the header said _M_cmpts is at offset 32 (because the string before it occupies 32 bytes in the new ABI), then every access to _M_cmpts in your binary will read from start_of_object + 32. That offset is a literal number in the machine code. It will never change at runtime.

The constructor and destructor work the same way. They are defined in the header and typically inlined by the compiler. Your binary contains the constructor code that initializes each field at its expected offset, and the destructor code that tears down each field at its expected offset. Both are hardcoded to the layout the compiler saw.

This means your binary doesn't just know how big a path object is. It knows exactly how to create one and how to destroy one, using the layout that was determined at compile time. If a different binary was compiled with different ABI flags, it will create and destroy path objects using a different layout, and neither binary has any way to detect the mismatch at runtime.

Two compilers, two layouts

With that background, here is what concretely differs between a path object compiled with the old ABI and the new ABI.

Old ABI: GCC 8, _GLIBCXX_USE_CXX11_ABI=0

Offset   Size   Field
──────   ────   ──────────────────────────
  +0      8     _M_pathname  (COW pointer → heap block)
  +8      8     _M_cmpts     (component storage)
──────
 16 bytes total

_M_pathname is a single 8-byte pointer. All the string metadata (length, capacity, and reference count) and the character data itself live in a single heap-allocated block that the pointer references.

New ABI: GCC 12, _GLIBCXX_USE_CXX11_ABI=1

Offset   Size   Field
──────   ────   ──────────────────────────
  +0      8     _M_pathname.ptr      (pointer to char data)
  +8      8     _M_pathname.length   (string length)
 +16     16     _M_pathname.union    (inline buf[16] or capacity)
 +32      8     _M_cmpts             (component storage)
──────
 40 bytes total

_M_pathname now stores its pointer, length, and either a 16-byte inline character buffer (for short strings ≤ 15 chars) or a heap capacity, all in 32 bytes, directly inside the path object.

The two layouts are not compatible. They disagree on the size of the object, the offset of every field after the first, and how std::string manages its memory internally. Code compiled against one layout cannot safely read or write an object created with the other.

The collision: reading 40 bytes from a 16-byte object

Here is the memory-level picture when the two ABIs collide. A shared library was compiled with the old ABI. It creates a std::filesystem::path object of 16 bytes. Your binary was compiled with the new ABI. It receives a pointer to that object and interprets it as a 40-byte struct.

What does the binary see?

Walking through each byte range:

Bytes 0–7 (_M_pathname.ptr): Both ABIs store a pointer at offset 0. The old ABI's COW pointer happens to point to a heap block where the character data eventually sits (after the length, capacity, and refcount fields). This is not identical to the new ABI's data pointer, but it's close enough that GDB can sometimes follow it and display the string content. Coincidental compatibility, not safety.

Bytes 8–15 (_M_pathname.length): The new-ABI consumer reads these 8 bytes as the string's length. But in the old-ABI object, bytes 8–15 are _M_cmpts, the component storage pointer or small-buffer state. A heap address interpreted as a string length produces a number in the trillions. Any code that uses this length to iterate over the string will read far past the end of any valid buffer.

Bytes 16–31 (_M_pathname.union): The consumer expects 16 bytes of inline string buffer or capacity here. But the old-ABI object is only 16 bytes long. These bytes don't belong to the path object at all. They are whatever happens to sit in adjacent memory: another local variable, alignment padding, freed heap metadata, part of a different object. The content is uncontrolled and unpredictable.

Bytes 32–39 (_M_cmpts): The consumer reads these 8 bytes as the component storage. Again, well outside the object. Pure garbage.

The binary is reading a 40-byte struct from a 16-byte region. The first 8 bytes are roughly compatible by accident. The next 8 bytes are wildly misinterpreted. And the final 24 bytes are whatever happened to be adjacent in memory.

What libstdc++.so expects

If the consumer calls a member function like parent_path(), the call doesn't stay inside the binary. parent_path() is implemented in libstdc++.so, the system's shared C++ standard library. That shared library was built with the new ABI. It expects every path object it receives to be 40 bytes laid out according to the new-ABI specification.

The call chain goes like this:

  1. Your binary passes a const path&, a pointer to what it believes is a 40-byte object
  2. libstdc++.so's parent_path() dereferences that pointer and reads the object's fields using new-ABI offsets
  3. It reads _M_pathname.length from offset +8 and gets a garbage value (it's actually the old-ABI _M_cmpts field)
  4. It reads _M_cmpts from offset +32 and gets garbage (24 bytes past the end of the real object)
  5. When it tries to use any of these values (iterating path components, reading the string, checking bounds), it dereferences invalid pointers or reads nonsensical lengths

The result is a SIGSEGV inside libstdc++.so, in a function that is perfectly correct. The function is doing exactly what it should: reading fields at their documented offsets. The problem is that the object it received was built to a different blueprint.

But in the real-world incident, the crash didn't require a method call. It came from something more fundamental: the destructor.

Why the destructor crashes

Even if you never call parent_path() or any other member function on the mismatched object, the destructor alone is enough to crash. Here's why.

C++ destroys class members in reverse declaration order. For std::filesystem::path, the members are:

class path {
    string_type _M_pathname;   // destroyed second
    _List       _M_cmpts;      // destroyed first
};

The destructor starts with _M_cmpts. In the new-ABI layout, _M_cmpts sits at offset +32. But the old-ABI object is only 16 bytes. Offset +32 is 16 bytes past the end of the object.

When the new-ABI destructor runs on the old-ABI object:

  1. It reads _M_cmpts at offset +32. This is outside the object — whatever sits in adjacent memory is interpreted as a unique_ptr<_Impl> (a pointer to the component list implementation)
  2. If that garbage value is non-null, the unique_ptr's destructor calls _Impl_deleter::operator() on it — dereferencing a garbage pointer
  3. SIGSEGV: the garbage pointer (in the real incident, 0x1a — a string length leaked from an adjacent COW control block) refers to unmapped memory

The destructor never even reaches _M_pathname. It crashes on the first member it tries to destroy.

If the garbage at offset +32 happened to be zero (null pointer), the unique_ptr destructor would skip the delete and proceed to _M_pathname.~basic_string(). That destructor has its own mismatch problem: its SSO check compares the data pointer (at offset +0) against the inline buffer address (at offset +16) to decide whether to call operator delete. The old-ABI COW pointer at offset +0 doesn't point to offset +16, so the destructor calls free() on the COW pointer — an interior pointer into a control block, not a valid free() argument. Either way, the program crashes.

This also explains why the crash is non-local: the old-ABI library that created the object runs perfectly fine. Its destructor would have cleaned up the 16-byte object correctly using the old-ABI layout. But if the object crosses the boundary and the new-ABI consumer's destructor runs instead, that destructor operates on a layout it doesn't understand. The fault is at the boundary, not in either side's code.

C++ types are not self-describing

The fundamental issue is that C++ objects carry no runtime metadata about their layout. A std::filesystem::path doesn't have a tag saying "I am 16 bytes" or "I am 40 bytes." The compiler bakes the layout into the consuming code, and the consuming code trusts that every object it receives matches that layout. There is no runtime check.

When two separately compiled binaries disagree on the layout, nothing catches the mismatch:

  • Not the compiler: it only sees one translation unit at a time, and each side compiles cleanly against its own version of the header
  • Not the linker: it checks symbol names, not type layouts. If the symbol crosses through C linkage or void*, the linker sees matching, undecorated symbols on both sides
  • Not the runtime: there is no layout metadata to compare. The pointer is dereferenced directly, using the baked-in offsets

This is why ABI mismatches are among the hardest bugs to find. The code is correct. The logic is correct. The types match in source. Everything compiles and links cleanly. And then a field access at the wrong offset segfaults, and the crash shows up inside libstdc++.so, in code you didn't write and can't easily debug.

The defense is straightforward but requires discipline: build everything in the dependency tree (your own code, your third-party libraries, your prebuilt packages) with the same compiler, the same ABI flags, and the same standard library version. When that invariant breaks, the result is a silent, delayed, non-local segfault with no warning from any tool in the normal build pipeline.

Single Point of Failure

SEP 06, 2026 10 min read

Our artifact repository went down on a Thursday afternoon. By Friday evening it was restored from a three-day-old backup, but in between: building was impossible, tools wouldn't start, and even committing code was blocked. Every developer workflow, through seemingly independent paths, depended on the same service.

The infrastructure

The setup: a C++ monorepo built with Bazel, devcontainers for local development, Artifactory as the central artifact repository, and GitHub Actions for CI. On a normal day the pieces fit together seamlessly. Artifactory serves Bazel's external dependencies, hosts tooling for the devcontainers, stores pre-commit hook binaries, and caches build artifacts for CI.

Then Artifactory went down. Not degraded, not slow: unreachable. Every HTTP request to it timed out. What followed was an education in how completely a single service can embed itself into every layer of a development workflow.

The devcontainer won't start

The first step of any workday is spinning up the devcontainer. The image was pulled days ago and cached locally. Starting the container should be a purely local operation.

It isn't. The devcontainer's startup script downloads tooling from Artifactory on every launch: linters, formatters, internal CLI utilities. The script doesn't check whether the tools are already present from a previous session. It fetches unconditionally. With Artifactory unreachable, the script hangs on the first HTTP request, times out, and exits non-zero. The container refuses to start.

The workaround: dig through the startup scripts, comment out every line that contacts Artifactory, and hope the leftover tools from a previous session are sufficient. Some are. The devcontainer comes up in a degraded state with gaps in tooling. Not ideal, but at least there's a shell.

Nothing builds

With the devcontainer limping, the next step is to build some code. Bazel resolves external dependencies at the beginning of every build by evaluating repository rules declared in MODULE.bazel (or WORKSPACE, depending on the repo's migration status). These rules fetch archives from Artifactory: third-party libraries, internal shared packages, toolchain components.

The expectation: targets that don't depend on anything external should still build. Plenty of code in the repo looks self-contained.

The reality: no such targets exist. Even the most fundamental internal libraries have a transitive dependency on a shared data-types package (custom containers, vocabulary types, error handling primitives) distributed as a prebuilt artifact through Artifactory. This package sits at the very bottom of the dependency graph, pulled in by nearly every cc_library in the repo. Compiling anything, even a small test with two source files, triggers a fetch for this package. With Artifactory down, the build fails during the fetch phase before it even attempts compilation:

ERROR: An error occurred during the fetch of repository 'company_types':
   Tried to download https://artifactory.company.dev/bazel-remote/company_types/v3.2.1/...
   but it failed: connect timed out

Bazel does maintain a local repository cache, keyed by the content hash of each repository rule's inputs (URLs, SHA256 checksums, patches). If a previous build already fetched the exact same dependency version, Bazel can serve it from cache without network access. The shared data-types package hadn't changed, so in theory its cache entry should still be valid. But the cache only helps if it's warm. A freshly rebuilt devcontainer, a new machine, a cleaned output directory: any of these mean a cold cache and a mandatory fetch. And for any dependency that did change since the last successful build (a version bump, a hash update, a new transitive dependency), the cache entry is invalidated regardless.

This isn't a Bazel-specific problem. Bazel's dependency model makes it explicit (every external dependency is declared and fetched by content hash), but the same fundamental issue exists in any build system that resolves artifacts from a remote store. If that store is unreachable and the local cache is cold or stale, nothing builds.

Tools won't launch

If compilation is off the table, at least there's design work. The codebase includes an architecture visualization tool that runs locally, providing an interactive view of module dependencies and ownership boundaries. I used it the day before.

Opening it today fails. The tool's launcher performs a version check against Artifactory on every invocation, fetching metadata to decide whether an update is available before running the locally cached binary. With Artifactory unreachable, the version check times out. The launcher exits before it ever attempts to run the cached copy.

No offline fallback. No flag to skip the check. The tool simply doesn't start.

This pattern shows up constantly in internal tooling: a startup routine that contacts a remote service not because the tool genuinely needs fresh data to function, but because someone added an auto-update mechanism and never considered the failure mode. The update check is a hard dependency masquerading as a convenience feature.

Even git commit is blocked

At this point the ambition is minimal: rebase a branch onto main to resolve some known conflicts, then commit. No build required. Just git operations.

The project uses the pre-commit framework, which manages hook tool versions and installs them on demand. Several of these tools (a code formatter, a static analyzer, a license header checker) are distributed as binaries hosted on Artifactory.

The rebase fires pre-commit hooks on every replayed commit. The hook runner attempts to install the configured tool versions. Download fails. Rebase blocked:

[ERROR] Failed to install tool for hook 'company-format':
  Could not fetch https://artifactory.company.dev/tools/company-format/v2.4.0/...
  Connection timed out

The tools had been installed previously and cached in the pre-commit environment directory. But pre-commit's cache is version-pinned: if the hook configuration specifies a version that differs from what's cached, it discards the old environment and re-downloads. Someone had bumped the formatter version two days earlier. My local cache held v2.3.1. The hooks demanded v2.4.0. Artifactory was the only source, and it was gone.

For a plain git commit, there is at least a workaround:

git commit --no-verify -m "WIP: hooks skipped during outage"

This skips all hooks: not just the broken download, but also the ones that catch real problems (trailing whitespace, merge conflict markers, credential scanning). There is no way to selectively disable only the hooks whose tools are unavailable while keeping the local-only checks active. It's all or nothing.

For git rebase, the situation is worse. I could not find an equivalent --no-verify escape hatch. The rebase fires hooks on every replayed commit, and with no way to bypass the failing downloads, rebasing was simply impossible.

The graph nobody drew

Strip away the details of each individual failure and the picture is simple:

Five independent workflows. One backend. The failure mode is identical in each case: a synchronous, blocking request to a remote service with no fallback, no graceful degradation, and no offline mode.

Nobody designed it this way. The coupling accumulated through years of reasonable, isolated decisions:

  • Distributing tools through Artifactory is convenient. It provides versioning, access control, and a single source of truth.
  • Adding a freshness check to tool launchers seems responsible. Nobody wants to run a stale linter.
  • Pinning pre-commit hooks to exact artifact versions ensures reproducibility across developer machines.
  • Fetching Bazel dependencies from a central artifact store is how Bazel is designed to work.

Each decision was sound in isolation. In aggregate, they created a system where one service going down makes every other workflow non-functional. Not degraded, not slower: completely dead. The definition of a single point of failure.

The recovery and its aftershocks

Artifactory was restored Friday evening from a backup. Whether the outage was caused by a technical failure or a security incident was never clearly communicated; the recovery took priority. The backup was three days old. That gap had consequences.

Lost artifacts. Every package published between the backup snapshot and the outage was gone. Internal libraries that teams had built, tested, and released during those three days simply no longer existed in the store.

Dangling references. MODULE.bazel files and lockfiles across the repo pointed to artifact versions that no longer existed. Each of these had to be identified and either rebuilt from source and re-published, or rolled back to a version the restored backup still contained.

Stalled merge queues. CI builds that depended on recently published packages failed with "artifact not found" errors. Merge queues backed up while teams scrambled to re-publish their dependencies in the correct order (respecting the dependency graph between packages).

Cache mistrust. Developers questioned whether their local Bazel caches were consistent with the restored Artifactory state. Many wiped their repository caches entirely, which meant re-downloading everything from a now heavily loaded, freshly restored instance.

The outage itself lasted barely a day, but the stale backup turned it into roughly a week of reduced velocity when accounting for the recovery tail.

Building for resilience

Artifact repositories go down. The question is not how to prevent every outage; it is how to keep developers productive when it happens.

Offline-capable devcontainers. Bake essential tooling into the container image itself rather than downloading it at startup. If a startup script fetches tools, it should check for existing binaries first and tolerate download failures with a warning rather than an exit. Running yesterday's formatter version is better than not starting the container at all.

Pre-fetched Bazel dependencies. Bazel supports vendoring external dependencies into the repository (bazel vendor), and bazel fetch //... can warm the repository cache ahead of time. A CI job that periodically fetches all external dependencies and either vendors them or populates a shared cache ensures that developers can build without live access to the artifact store. The tradeoff is repository size and freshness, but for critical-path dependencies (like the shared data-types package at the bottom of the graph) it is worth it.

Fault-tolerant tool launchers. Any tool that performs a version check on startup should treat the check as best-effort. If the remote is unreachable within a short timeout, run the cached version and log a warning. Running a slightly outdated binary is vastly preferable to running nothing.

Resilient pre-commit hooks. pre-commit's caching can be made more durable by pinning hooks to commit SHAs rather than mutable version tags, reducing cache invalidation from tag drift. For critical hooks, the tool binaries can be committed directly into the repository, eliminating the runtime download entirely. This costs repository space, but it means git commit never depends on network access.

Graceful CI degradation. Build pipelines should distinguish between "artifact temporarily unavailable" and "build genuinely broken." Fetch timeouts should trigger retries with backoff, and merge queues should be able to pause and drain gracefully rather than failing every enqueued PR.

None of these measures are exotic. They are the difference between a system designed only for the steady state and one that plans for the day the steady state breaks.

Shutting the laptop

The most productive thing I could do during the outage was close my laptop and take the day off. That is the honest conclusion of attempting four increasingly basic tasks (starting a container, building code, opening a tool, committing a change) and failing at all four for the same underlying reason.

I had never spent time thinking about this scenario, and the extent of the damage was genuinely surprising. The outage did not reveal a bug in any individual system. It revealed an architecture: one where every layer of the development workflow had independently decided to depend on the same remote service, and not one of them had a plan for when it was gone.
